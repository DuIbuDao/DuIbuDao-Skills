# 批量调价审核流程

## 1. 先试改再批量
1. 从差距小（如 ±10% 以内）的批次里挑 1–2 条单 SKU、有库存的链接试改。
2. 只改目标字段（如 Retail price），其他字段不动；记录改前/改后价、库存、状态、是否触发审核，截图。
3. 后台和买家端两边都核对；买家端过不了验证就请老板用手机看一眼。
4. 检查是否在秒杀/闪购中：活动价不变时，划线折扣会跟着变，要提醒。

## 2. 审核表（老板没点头前一条不改）
- 每行一个 SKU：商品 ID、seller SKU、品名、现价、参考价（注明数据日期）、目标价、涨跌幅、库存、是否在活动中、活动价/折扣、审核列。
- 分「摘要 / 涨价 / 降价」sheet，按涨跌幅从大到小排；已试改的放最上面作参考并高亮。
- 审核列做成下拉：同意 / 驳回 / 暂缓。
- 老板可能决定自己手改：那就停止一切改价，审核表留作对照。

## 3. 活动价只读抄录
- 后台活动页常无导出、每页有滑块：只看不改，分批存 tsv，抄完再用脚本回填审核表（回填前备份原表）。
- 不在活动里的标「无」，不要标「待查」。
- 有硬截止（活动结束时间）时先报进度和预计完成时间。
- 中途掉线/重启：保存已抄数据，报告进度，按登录流程恢复，不要自作主张重启别人的进程。

## 4. 变体匹配
- 先按 SKU 精确对；对不上时用品名里的中文颜色去对英文变体名做第二轮。
- 同价多色、找不到对应颜色名的**留空不猜**，状态写「SKU 未对上（待确认）」，候选变体写进表里。
- 价格对不上的行标黄写清两个价，并回查是不是匹配错了变体（常见原因）。
- 异常单独汇报：活动价 ≥ 原价、折扣异常偏高等。

## 5. 审核表按系列归组
老板要连续改价时，把同系列、相似 SKU 排在一起，不要按字母或导出原序让同款散开。
- 结合 SKU 前缀、后缀和产品品名识别同系列（常见是前缀尺寸、后缀颜色、中间核心款号，以实际编码规则为准），再按尺寸、款式、颜色排列。
- 用品名交叉核对；不能确定的相邻放置并标注，不强制合并成一行。
- 加「系列索引」方便跳转。已填写的价格、销量和审核意见全部保留，只改排列，不合并数据。

## 6. 用销量判断闪购价是否合理
若要判断某价格区间或闪购价是否合理，在审核表里补销量，且：
- 统计范围是全店所有产品，不只调价清单；零销产品也保留。
- 各发货渠道分开列，再给合计。周期用 15 / 30 / 90 / 180 天（或任务指定的档位），截止到上一完整日，避免当天未结束的数据。
- 取消订单剔除；未付款件数单独备注；退货是否从销量中扣减要写明口径，未扣就注明。
- 按件数统计，不要把订单行数当成销量。订单表与商品主表 SKU 对不上时，把「确实没销量」和「数据未匹配」分开标注。
- 已结束活动的历史闪购价必须标明是历史价，不得当成当前价。
- ERP 或订单里的单价往往不是买家实付的闪购成交价。其他价格期间产生的销量，不能直接当作该闪购价合理的证据。缺当前活动价或可靠实付数据时如实标明，先不下「价格是否合理」的结论。
