# 闪购与叠加优惠定价

给跟亚马逊价对齐的 TikTok Shop 设定或审核闪购价、叠加优惠时使用。每周只对原价、建议上架/删除，用 `weekly-amazon-price-check`。做批量改价审核表或只读抄录活动价，用 `bulk-repricing-review`。只出提案，老板没点头前不改后台。

## 先对齐划线价

- 全店原价（划线价）先统一到采用的亚马逊现价 × 2 + 10。商城里的促销力度靠这条原价撑出来；原价不齐，折扣看起来乱，也更容易打穿亚马逊。
- 已经倒挂或低于亚马逊的原价，先改原价再谈闪购，不要在错误原价上做活动价。

## 成交价红线（按库存来源）

看的是按官方可同时生效的叠加栈算完之后的预估成交价，不是闪购标签上的折扣率，也不是把互斥的券都加在一起。

- 默认（含 MCF / 亚马逊仓的货）：成交价必须高于亚马逊现价，最低按亚马逊 + $0.01。动销慢一点先不管，不要为了这些货去打穿亚马逊。
- FBT（商家海外仓）库存，以最早一批到货日算库龄：正常应在到货约 3 个月内销完。3 个月以内，成交价仍不得低于亚马逊。
- 只有到仓已超过约 3 个月、按当前速度仍难以销完的 FBT，才允许清仓到亚马逊以下。具体清仓价出提案给老板审，不要自行改后台。
- 对不上亚马逊现价的行，闪购建议价留空，不要猜。

## 平台与券的硬限制

- 同时只能开一条闪购。不要提案并行开多场（比如把爆款、去库存、清仓拆成三条同时跑）。不同目的要收进这一条，或等当前场结束再开下一场。
- 粉丝券、满减、满件折默认保留：粉丝券用来积攒账号粉丝流量，满减和满件折也是清货手段。不要为了「折扣看起来干净」就建议关掉。
- 商家券每单一张，系统自动取减额最大的那张。粉丝券、普通店铺券、聊天券、评价券、折扣码都算商家券，互不叠加。满件折不是券，是购物车级促销，可以和闪购、一张商家券同时用。正确叠加栈是：闪购 + 满件折 + 一张最大商家券。不要把粉丝券和店铺满减当成会同时生效来反推，那样建议闪购价会偏高，口径是错的。
- 反推建议闪购绝对价时，默认按「闪购 + 满件折 + 一张最大店铺券」，先不算粉丝券。若满件折有多档，要让各档路径的单件成交都不低于上面的红线。只按原价打一个折扣率、不把可叠加的券和满件折算进去，容易打穿亚马逊，或触发平台「叠加折扣超过 80%」一类警告。
- 店里若还有粉丝券，在风险列标明：买家若用粉丝券替代店铺券，成交价可能低于红线。风险列只作参考，不要当成要填进闪购的价格。聊天券、评价券、平台券等未计入的优惠，实际成交还可能再低，要在说明里写清。
- 已经打到约 80% off 仍然几乎没销量的，再降意义不大，不是价的问题。不要再往 80% 下面切。若是滞销 FBT，维持清仓价继续出清，或等老板点头后再考虑下架。

## 审核表

- 至少包括：销量（写明周期和是否剔除取消）、FBT 现有库存、按「库存 ÷ 日均销量」估算的预计售罄天数（口径写明；零销写「按当前速度无法售罄」，不要编日均）、FBT 最早一批到货日、采用的亚马逊现价、目标原价、建议闪购绝对价、按上述叠加栈叠完后的预估成交价、粉丝券风险参考（如有）、审核列。FBT 现有库存等关键列必须可见，不要隐藏。
- 表里还要能对上 FBT 货品标识（如领星「管理货物」的商品编号），按文本写入，避免被表格软件改成科学计数法。
- 在不打穿红线的前提下，可以按动销建议闪购深浅（卖得好的浅打、卖得差的深打），但不要为此再开第二条闪购，也不要把复杂分档堆成老板看不懂的大表。优先把「FBT 超 3 个月仍有库存、按当前速度销不完」标清楚。
- 全程只读导出与测算。老板在表里审核通过后，只改他点头的那一条闪购价，不顺手改原价、券或其他活动。
